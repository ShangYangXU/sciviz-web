## 1. 定位

> **把模型训练、评估与数据分析的数据流，变成可校验的契约。**
> 可视化是它的界面，可复现是它的产物，可被 agent 操作是它的用法。

一句更短的版本：**让数据流可被机器读懂。**

### 1.1 项目初衷（2026-10-02 补充）

这个项目起源于作者在使用 AI 编写深度学习代码、分析数据和让 Agent 做实验时遇到的困扰：代码散在许多函数里，阅读时容易迷失调用关系与数据流；分析产生的图表越来越多，难以管理并对应到具体的实验；Agent 执行了哪些步骤、改了什么、怎么得到结果，也常常不够直观。

作者是一名在读研究生，也在自己的研究中使用和持续完善 SciViz。对外介绍应保持朴实，说明项目仍有需要打磨的地方，并提供问题反馈入口，由作者持续排查和修复。

因此，SciViz 希望成为人与 Agent 共用的实验工作台：Agent 能操作和运行实验，人能实时查看进度、每一步的输入输出、参数和结果，看清模块之间的接口与连接关系，并在需要时接手。这份初衷补充现有定位，具体能力仍以现行契约和实现为准。

这不是"又一个节点编辑器"。节点编辑器是四十年的成熟范式（LabVIEW、Simulink、KNIME、Orange、ComfyUI），本身不再是差异点。差异点在于：**大多数节点工具只让流程"跑起来"，本项目要让流程"立得住"**——每一步承诺什么、谁保证、违约怎么报，全部显式化。

## 2. 目标用户

不按学科划分，按**行为**划分：

> 用机器学习/深度学习做研究，需要跑通"数据 → 特征 → 模型 → 评估 → 出图"整条链路，并且要能**复现**、能**交给别人接手**、能**写进论文**的研究生与研究者。

典型痛点场景：

1. 流程散在多个脚本与 notebook 里，参数改了哪一处自己都记不清。
2. 半年后重跑，结果对不上，且不知道是哪一步变了。
3. 师弟师妹接手，只能靠口头交接；论文里的图无法追溯到具体配置。
4. 换了数据，旧结果仍在界面上，且没有提示。
5. 想让 AI 帮忙跑或改流程，但没有一个 AI 能读懂的载体。

## 3. 问题陈述：什么叫"数据流是非标准的"

1. **接口是隐式的。** 每一步的输入输出形状、单位、轴序，只存在于作者脑中与临时 `print` 里。
2. **同一变换有多种写法。** 去均值与否、在哪一步分帧、归一化统计量算在全量还是训练集——各人各样，且大多无声地错。
3. **无身份。** 数据换了、代码改了，系统仍按旧结果继续，且不报警。
4. **无血缘。** 论文里那张图，追溯不回它是哪份配置、哪份数据产出的。
5. **不可被机器操作。** 流程没有机器可读的表示，因此 agent 无法操作，CI 无法校验。

## 4. 价值主张与对应机制

价值主张不是功能列表，每一条都必须有架构机制兜底，否则就是口号。

| 主张 | 架构机制 |
|---|---|
| **可复现** | 端口契约（类型/轴序/单位/拆分） + 算子版本与实现哈希进指纹 + 数据集内容哈希 + 随机性三级声明 + 运行清单 + 显式列出不可复现项 |
| **可复用** | 算子词汇表有界 + 边界标准化 → 图可拼装、可被他人接手；内部实现自由，不牺牲可定制性 |
| **可被 agent 操作** | 机器可读 IR + 有界动作空间（补丁而非任意代码） + 逐边验证 + 稳定错误码 + 自描述 Schema + 补丁审计 |
| **计算数据默认不出本机** | 纯本地执行、零必需服务端依赖；可选远程模型只发送用户明确选择的上下文，默认不含行值/权重/图片像素，每次外发先审计。使用本地模型时保持零外发 |

**关键洞察**：可复现、可复用、可被 agent 操作，这三件事要的是**同一套底座**。所以标准化不是为复现付出的成本，而是一份投资同时买到三样东西。这是本项目最本质的经济性。

## 5. 与同类产品的定位差

| 类别 | 代表 | 它们的边界 | 本项目的差异 |
|---|---|---|---|
| 桌面节点式数据分析 | KNIME、Orange、DAWorkBench | 能力强，但要装桌面软件；默认不强制数据契约（DAWorkBench 有"数据探针"但那是**查图上数据点**，不是查节点输出契约） | 浏览器零安装 + 契约强制 |
| 节点式工作流 UI | ComfyUI | 自由度极高，但**可复现性的反面教材**：无类型约束、节点包独立版本化、老工作流会静默失效 | 借用它的交互，反转它的取舍：标准在边界上 |
| 代码优先的可复现管线 | Flyte、TFX/MLMD、Hamilton、Metaflow | 契约做得很实（类型、artifact、血缘），但没有可视界面，门槛高 | 把同一套契约做到可视、本地、可交互 |
| 浏览器内跑真 Python | JupyterLite、Preswald、Flowfile WASM | 技术路线已验证，但是 notebook / 代码优先 / ETL，不是"带契约的节点图" | 节点图 + 契约 + 探针 |
| 科研绘图与统计 | Origin、Prism、JASP、jamovi、Hiplot | 解决"出图与统计"，不解决"流程" | 与它们互补，不竞争 |

**结论**：范式不独特，技术元素不独特，**"浏览器零安装 + 节点图 + 真 Python + 强制数据契约"这个组合是独特位置**。这是位置优势而非技术壁垒，壁垒要靠算子正确性与领域纵深去挖。

## 6. 范围

**做**

- 数据导入、列式存储、可视化预览（已完成）
- 数据变换与特征算子（部分完成，走真引擎）
- 模型定义 / 训练 / 超参 / 评估（当前为模拟，接口是真的）
- 出版级图表与导出
- 契约校验、运行清单、工程文件
- agent 工具面与 headless CLI

**不做**

- 通用 BI / 数据大屏
- 云端协作与托管
- 一键 AutoML 与模型 zoo
- 数据标注
- 绑定单一学科领域（领域节点库以可插拔扩展形式提供）

## 7. 路线图

详细阶段与完成判据见[架构总纲 §10](./架构总纲.md)。摘要：

| 阶段 | 一句话 |
|---|---|
| P0 | 立契约：类型描述符、算子清单、静态校验器、错误码、算子版本进指纹、数据内容哈希 |
| P1 | 统一执行面：Job 模型、模拟适配器化、指纹作缓存键、持久化 |
| P2 | 工程化：`.sciviz` 工程文件、运行清单、headless CLI |
| P3 | agent 面：IR Schema、工具面、补丁审计 |
| P4 | 扩展与真训练：节点包契约、版本迁移、真训练适配器 |

**P0 的入场判断**：在 P0 完成之前，不新增算子、不做界面优化。理由是每新增一个未声明契约的算子，都要在 P0 里补一次债，而当前的债已经在产生错误结果（改了算子代码，旧结果仍显示为最新）。

## 8. 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **标准化的收益与成本倒挂** | 契约越严，越可能排除真实研究的"例外情况" | 逃生舱是设计的一部分：`custom.script` 内部任意，边界仍受约束（契约规格 P1）。标准可局部退出，但退出即被记录 |
| **浏览器性能上限** | Pyodide 在百万行级数据上会吃内存与算力 | 数据留在 Python 侧、只回传摘要与 head（现有做法正确）；重训练走 `local-process` 适配器；不把性能当作 P0–P2 的指标 |
| **自由与标准的张力** | "像 ComfyUI 一样自由"与"可复现"在同一根轴对立 | 架构层面固定切法（A2），并写进契约第一原则，避免后续反复摇摆 |
| **agent 的替代方案是直接写脚本** | 若图给不了脚本给不了的东西，agent 没有理由用它 | 死守四条：边界约束、增量重算、逐边验证、有界动作空间（架构总纲 §7.1） |
| **生态冷启动** | 没有节点生态就没有长尾场景 | P4 才做节点包契约；在此之前先把核心契约与 23 个内置算子的质量做扎实 |
| **定位再次漂移** | V2 曾把项目错误地绑定在 PHM 上，并因此影响了一轮技术选型判断 | 本文档为定位的唯一来源；V2 顶部已加废弃标记 |

## 9. 待你拍板的问题

1. ~~**契约严格度**：`E_SPLIT_LEAK` 这类静态错误是"阻断"还是"强烈告警"？阻断更安全，但会挡住探索式研究；建议默认阻断，并允许在工程级别显式降级为告警（降级记录进运行清单）。~~
   **已决（2026-09-22）**：拆成两件事，不再是一个开关。
   **判据照旧严格**（`validate` 该报照样报 `E_*`，拖一条类型不对的线照样被拒，`E_SPLIT_LEAK` 仍是错误而不是警告）；
   **但它不再是整张图的写入闸门** —— 补丁只被"能归因到某条 op 本身"的拒绝拦住，其余 L1 结果如实报告、由人和 agent 决定要不要接着改。
   原因是用户的实际用法：把许多子实验收进一个子空间省地方，画布上长期存在搭到一半的地方；
   整图 L1 当闸门时，agent 会**一个块都改不动**（见[开发日志](./开发日志.md) 2026-09-22 那一节）。
   "工程级降级为告警"因此不需要了：降级与否是**看的人**的事，不是写入的事。规格见[数据契约规格](./数据契约规格.md) §7。
2. **`any` 的容忍度**：内置算子是否一律禁止 `any`？建议禁止，只留探针与适配器两类透传节点。
3. **P0 是否冻结新功能**：建议冻结，直到契约与指纹两处缺陷修完。
4. **P2 的 headless 入口形态**：独立 CLI 包，还是先做成 Node 脚本？建议先脚本，验证分层后再抽包。
