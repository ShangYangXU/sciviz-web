## 6. 可推后（不影响现在用）

### T18 · 跨运行缓存（**已收**）

- **现象**：每次 `run` 都是新的引擎会话，同一工程重跑全部重算。
- **做法**：宿主进程里留一份结果（`sciviz_host/cache.py`，按输入指纹的 LRU，单条行数超上限不缓存）。
  **判据在主线程**：算子声明 `deterministic` / `seeded` 才发 `cacheable`（R6.4），
  `stochastic` / `volatile` 一律不发 —— 两个训练算子声明 `stochastic`，所以它们**永远重算**。
  命中时 `nodeResult.cached` 一路回传：日志、运行清单 `nodes[].reused`、报告里单列一节。
- **加缓存时当场撞出一个真缺陷（已修）**：指纹里"上游"那一项原本只记**版本号**，
  而版本号每次都从 1 重新数 —— 于是"结构相同、上游喂的是另一份数据"的两张图，下游指纹一模一样。
  实测：两个实验的"时域特征"被判成同一份缓存，第二个实验直接拿到第一个实验的数，
  而清单、日志、数字看起来全都正常。现在上游**指纹（内容）+ 版本号**两条都记。
  顺带补上：`data.source` 的指纹此前不含**数据集内容哈希**（只有列名与时间列）——
  "换了数据但列一样"不会被察觉（R3.2 的那一类）。
- **判据**：宿主 unittest 9 项（命中 / 不命中 / 说不许复用就一次都不许命中 / 太大不缓存 / LRU /
  **命中之后数据仍然取得到**）；
  内核 2 项（`cacheable` 由确定性等级决定、`reused` 记进节点状态）+ 指纹 2 项；
  本机实测：同一张真实数据（104.8 万行）的图连跑两次，第二次三个节点全部复用，
  节点耗时合计 **2503ms → 0ms**（数据 374→0、分帧 586→0、时域特征 1543→0）。
- **仍未做**：缓存不落盘（宿主重启即失效）；CLI 每次仍要重新解析那份 CSV（输入侧开销，
  与算子无关）—— 想省这一段得给数据集也做内容级缓存，那是另一条。

> **盲测当场抓到的第三处（已修）**：第一版缓存只存了**摘要**，命中时没把输出对象放回
> 这一次会话 —— 于是 `run` 之后紧跟的 `inspect --rows 1` 报"上游节点还没有求值结果"，
> 而节点状态写着 ready。现在缓存连对象一起留（`runtime.outputs_of` / `put_outputs`），
> 命中时放回当前会话；`MAX_ROWS` 那道闸也因此更必要（快照占的是真内存）。

### T19 · 64 轮定点循环改成按拓扑序一次（**已收：不改，理由见下**）

- **原判断**：正确但不必要，图只有几十个节点，不阻塞任何事。
- **复核后的结论：那个循环是有用的，"按拓扑序一次"会把它做坏。**
  端口不是静态的 —— 拆列（`data.columns`）的端口等于**上游那张表实际的列**，
  函数节点的端口来自签名解析的结果。这些只有在上一轮真的算完之后才知道，
  所以调度必须"算一轮 → 拿新端口重新规划 → 再算一轮"，直到没有该算的为止。
  一次拓扑排序做不到这件事：规划时它还不知道那些端口长什么样。
- **而"浪费"这件事并不存在**：同一张图里每个节点仍然只算一次（改完全新图的实测是
  4 个节点各算一次、版本号都是 1），指纹没变的节点一个都不重算。
  这两条早就有钉子：`kernel.test.ts` 的「全新图一轮结算」与
  「一切都没变：一个节点都不重算」，加上「拆列节点的端口在上游算完之后才存在，且第二轮就补上」。
- **顺带补的一处**：无头侧此前没人提供 `columnsOf`，所以那条"第二轮补上"在 CLI 路径上
  从来没成立过（拆列在 CLI 里永远算不出来）—— 现在核自己从刚算出的输出摘要里补一份
  （G4 那笔提交），循环因此在两条路径上都有意义。

### T20 · 示例数据不再是 56MB 的明文件（**已收，做法与最初设想不同**）

- **原来的现象与判断**：`sciviz-web/public/samples` 有 56MB，那个 1,048,576 行的 CSV 在 git 里，
  仓库又没走 LFS —— 结论写的是"每次 clone 都要拉它"。
- **实测把这个判断修了一半**：git 的 pack 本来就是 zlib 压过的，那份 CSV 在 **pack 里约 5.6MB**，
  所以 clone 从来不是 56MB；**56MB 出现在三处：工作树、`dist/`、桌面壳的安装包**。
- **做法**：仓库里存 `boiler2-full.csv.gzip`（**58.7MB → 5.6MB，9.5%**），界面用浏览器自带的
  `DecompressionStream` 解（不引库、不是构建期步骤），`verify-operator-truth.mjs` 用 Node 的 zlib
  直接读，另给一个 `scripts/unpack-samples.mjs` 供"想用 Excel / pandas 看一眼"的人。
  扩展名是 `.gzip` 不是 `.gz`：`.gz` 会被静态服务器当成预压缩变体并加 `Content-Encoding: gzip`，
  浏览器替你解一遍、我们再解第二遍就炸（实测踩过，客户端两种行为都接得住）。
- **没有按需下载 / 没有走 LFS 的原因**：两条路都要能连上托管方，而本机现在连
  `github.com` 与 `raw.githubusercontent.com` 都不通 —— 那样做出来的东西**没法验**，
  而且对同样网络环境的用户等于"示例数据永远取不到"。历史里的那份 58MB blob 也仍在
  （只有重写历史才消得掉），所以本条的收益说清楚是**工作树 / dist / 安装包 −53MB**。
- **判据**：`npm run e2e` 42/42（示例数据自动载入、时间轴、真值那几条都走这条路径）；
  仓库里那个文件从 58,728,723 字节变成 5,562,130 字节。
