# MCP 性能分析与加速方案

> 日期：2026-10-01（Asia/Shanghai）  
> 状态：分析与实施建议；尚未实施产品改动，不替代现行接口规格。  
> 分析对象：当前工作树中的外部 MCP、CLI、Facade、无头运行、实时画布桥、宿主与相关文档。工作树已有大量未提交改动，本报告以文件实态为准。  
> 规范依据：[方案V3](./方案V3.md)、[架构总纲](./架构总纲.md)、[数据契约规格](./数据契约规格.md)、[Agent面设计](./Agent面设计.md)、[接口文档](./接口文档.md)、[MCP面设计](./MCP面设计.md)。

## 1. 结论与建议

**可以加速，并且优先改动能同时提高质量。最值得做的是减少不必要的模型往返、消除隐式重算、修复工具契约和协议缺陷。**

当前 MCP 已经是常驻进程，工具经进程内 `runCli` 转发。本机实测，清单热调用只需约 6–8 ms；因此把 stdio 换成 HTTP、再做一次“常驻化”，不是当前主要收益来源。外部模型每次理解工具、决定下一步、生成参数的时间没有在本次实测中采集，不能把用户感觉的总耗时全部归给 MCP 传输。

已经实证三个问题：① 全量清单超过截断上限，正常发现能力的第一步就丢失结构化完整性；② 结果行值分页实际上在反复启动新运行，随机节点两次读相同行也会得到不同结果；③ 工具运行期间的协议心跳回包被 CLI 的全局 stdout 捕获，心跳超时且工具输出受污染。此外，共享 ToolSpec 存在 surface 参数缺失、全局串行队列会堵住无关读取、实时画布默认截图和运行完成语义不够可靠。

推荐顺序：**先修契约、协议、文档和结果真实性；再把运行与读取解耦；随后提供有边界的批量读取与通用执行组合，减少模型回合；最后根据埋点决定缓存、调度和图像渲染优化。** 全过程复用原有契约与核，不给 MCP 另建计算逻辑。

## 2. 分析范围、实测与证据等级

### 2.1 范围

按仓库规定顺序审阅六份基础文档，再检查 MCP 设计、对话栏设计、文档索引、待办、工具注册表、协议壳、CLI、工程装载、结果读取、无头核、实时画布桥、浏览器运行入口、宿主会话、缓存与现有 MCP 检查。开发日志用于追踪设计原因；历史记录与现行规格分开判断。

本次只新增分析材料和隔离探测文件；没有修改产品源码、既有实验工程、模型配置或凭据，没有发起外部模型请求，没有启动训练。真实执行仅使用 2000 行、两列合成数据，以及一个用于验证读数一致性的随机函数。隔离工程通过既有 `new` / `patch` 创建与修改。

证据分为三类：**实测**是本次运行观察；**源码确认**是可定位的控制流；**推断/建议**是需要后续测量或实现验证的影响。下文的优先级评分是工程判断，不是测出来的性能分数。

### 2.3 尚未量到的部分

- 外部 agent 的模型推理时间、工具发现策略、工具结果是否同时摄入 text 与 structuredContent、真实重试次数和完成率。

## 3. 系统调用链：时间具体花在哪

### 3.1 已保存工程路径

```text
外部模型决定工具与参数
  → MCP stdio / tools/call
  → 全局 Promise 队列
  → 参数变成 CLI argv，部分请求落临时 JSON
  → runCli 暂时接管进程 stdout/stderr
  → CLI 装载模块、解析参数
  → 文件读取 / 工程解析 / 契约校验
  → 必要时解析 CSV、算内容哈希
  → 新 HostAdapter / WebSocket 会话
  → 同一个 kernel.runGraph / 宿主算子与缓存
  → 取 head / 可选图像渲染
  → 关闭会话、写 run.json / report.md / index.json
  → JSON 文本解析、截断、MCP 包装
  → 外部模型读取结果，决定下一步
```

`runProject` 每次创建 `HostAdapter`，结束后 `adapter.close()`；`loadProject` 的 `parsedCache` 只活在一次装载里。宿主已有跨会话算子缓存，但这不会自动省掉工程读取、CSV 解析、哈希、上传、调度、运行清单写入。见 `src/agent/run.ts:346` / `:422`、`src/agent/project.ts:213`。

### 3.2 实时画布路径

```text
外部模型 → MCP 队列 → CLI canvas
  → GET /agent/config 获取进程令牌
  → POST /agent/canvas/call
  → 宿主选择可见/聚焦页面
  → 页面 WS + 页面自己的串行队列
  → 激活画布、等两帧、调用现有画布动作
  → 默认截图：克隆 DOM、递归复制计算样式、SVG 光栅化、PNG/base64
  → WS/HTTP/CLI/MCP 把结果与图像回传
```

这条链操作浏览器内存，文件工具操作磁盘。两者会暂时不同，不能把磁盘读取当成实时画布的验证。宿主等待页面结果的上限是 65 秒，CLI 总等待是 70 秒；页面确认框、后台标签页的动画帧等待、截图都可能占用这段时间。具体占比尚未测量。

### 3.3 第一性原理模型

对真正有依赖的关键路径：

```text
任务总时间 = 模型回合时间
           + 工具等待与实际执行时间
           + 失败后额外回合/重试的时间
           + 人工等待时间
```

工具时间再拆成排队、装载、数据准备、计算、取证、序列化与传输。并行任务不能简单把所有调用时间相加；要观察关键路径和资源竞争。

可优化的根变量只有五个：**少问模型几次、每次给足所需信息、少搬重复状态、只计算该算的东西、及时判定何时完成或失败。** 校验是否保留不是加速变量；应减少重复执行同一判据，不能削掉判据本身。

例如，若某个任务实测模型时间占 80%、本地工具占 20%，即使把本地工具变成零耗时，总体也最多快 1.25 倍。若一个任务有 12 次串行模型决定，每次假设 5 秒，把四次纯机械衔接移到服务侧，可省约 20 秒；把每次 7 ms 改成 1 ms 只省 72 ms。**这里的 80%、12 次、5 秒仅是解释公式的示例，不是本次用户任务的实测。**

## 4. 瓶颈排序与原文对照

评分采用“影响/证据确信度/实现成本”三个 1–5 档：前两项越高越强，成本越高越难。成本是相对工作量判断，不是工期承诺；质量缺陷优先于单纯耗时。

| 项 | 问题 | 影响 | 确信度 | 成本 | 优先级 |
|---|---|---:|---:|---:|---|
| B1 | 工具 schema 与实际调用不一致 | 5 | 5 | 2 | P0 |
| B2 | stdout 全局捕获污染 MCP 回包 | 5 | 5 | 3 | P0 |
| B3 | 清单截断与不完整结构化结果 | 5 | 5 | 2 | P0 |
| B4 | 结果分页反复运行，跨页可能属于不同实验 | 5 | 5 | 4 | P0→P1 |
| B5 | 实时 run 未提供可信完成屏障 | 5 | 4 | 4 | P0→P1 |
| B6 | 历史文档混入现行操作指引 | 4 | 5 | 2 | P0 |
| B7 | 全局队列阻塞无关读取/取消 | 4 | 5 | 4 | P1 |
| B8 | 发现、改图、取证需要过多模型回合 | 5 | 3 | 3 | P1→P2 |
| B9 | 每次装载/哈希/上传，缓存前仍有重复工作 | 4 | 4 | 4 | P1→P3 |
| B10 | 默认截图、全图详细投影与重复文本 | 3 | 4 | 3 | P1→P3 |

### B1：共享注册表只统一了工具名字，还没统一 surface 的调用契约

文档原文，MCP 设计 §2 M2：

> “MCP 工具集合等于 `TOOLS.filter(surfaces includes 'mcp')`，且每项都有对应 CLI 映射。”

源码与实测：`tools.ts:127` 的 catalog schema 是空对象且拒绝额外属性，但 MCP 映射接受 `type`；`:138` 的 validate schema 只有 columns，不允许 `file`，然而 CLI 必须有文件。实测 `{}` 合法于 schema，却得到用法错误；传入 schema 未声明的 file 才能成功。部分 explain 参数也只在映射层存在。

同时 `catalog` 的 JSON 分支先于类型选择，MCP 总加 `--json`；**即使偷偷传 type，也仍得到全量清单**。`plan` 接收 patch，但映射和 CLI 只做当前工程执行计划，不预演所传补丁。`undo` 声明 patchId/baseFingerprint，MCP 没转交，CLI 撤销分支也没按这些字段检查且输出散文。`inspect_figure` 声明 groupPath，但映射没转交，嵌套同名节点选择需要修正。

这类缺陷不是换提示词能修的。建议以共享逻辑规格生成各 surface 参数投影和绑定，文件侧 file 必填，Chat 侧可用当前工程；不复制两份算子或动作定义。为每个工具做“schema 合法最小输入→真实执行→结果”的契约测试，并证明声明字段被消费或明确拒绝。

工具效果声明也须同步：当前 inspect 标为 read，但 rows 实际会计算；canvas 把 status/inspect 与 patch/run 都包在同一 graph-write 工具里。实施时应在共享声明中按动作表达实际效果，让授权、并发和客户端提示依据真实行为，而不是仅凭工具名字判断。

### B2：所谓“进程内零开销”的实现有全局 I/O 副作用

文档原文，MCP 设计 §3.3：

> “进程内转发（约 0 ms）+ CLI 自身耗时。”

源码：`sciviz.mjs:2287` 直接改写 `process.stdout.write` / `stderr.write`。MCP 的 `ping` / `tools/list` 不进工具队列，直接写 stdout。工具执行期间它们的 JSON-RPC 回包因此被捕获进 CLI 输出。

隔离探测实证：延迟假宿主下，ping 600 ms 后超时；其回包出现在 canvas 工具的文本里，`JSON.parse(stdout)` 失败，`structuredContent` 消失。串行化所有 tool calls 没有解决控制消息的并发。

建议先把输出改为请求局部的 writer 注入，协议 stdout 始终归 MCP；进一步让 Facade 返回类型化对象，CLI 负责打印，MCP 负责包装。**不能直接删队列就开并发**，否则多个 `runCli` 互相接管 stdout，会产生更严重污染。

### B3：常规 catalog 已经每次截断

文档原文，MCP 设计 §5：

> “`catalog --json` 实测 61 KB。”  
> “> 64 KB 时截到 64 KB并追加……完整原文写到……文件。”

本次实际文本 68,765 B，已超门槛。`sciviz-mcp.mjs:247` 按字节切 JSON，可能切断对象或 UTF-8 字符；`:293` 的 `structuredContent.full` 放的是整个截断文本，而不是完整文件路径。于是完整 schema/错误表不能可靠地直接消费，还可能多一次文件读取和模型回合。

建议立即使用紧凑 JSON，作为缓解；永久方案是“目录摘要→指定类型详情”，加结构化分页和有界字段投影。超过预算时返回**仍合法、明确不完整**的 JSON 与 cursor/资源引用，不能把 JSON 字符串截一半后称为结构化结果。控制重复 text/structuredContent 的策略须考虑客户端兼容，不能未经验证直接去掉全部文本。

### B4：读取结果的动作在创建新实验

文档原文，Agent 设计 §5 G7：

> “与探针同源的值摘要。”

MCP 设计 §7 也写：

> “`sciviz_inspect` 带 `from=<manifestPath>` 时不再跑一遍。”

源码：MCP inspect 固定进入 `--canvas`；该分支只要有 rows，就走 `sciviz.mjs:1295` 的 `runProject`。指定历史 manifest 又不能取行，因为清单只存摘要。显式 `from=latest` 配 rows 仍会新跑。`runProject` 结束关闭 WebSocket，无法复用原会话取数。

实测三页产生三个 runId；随机函数同样两行读取两次，随机值不同。因此分页拼接会把多个实验混在一张表里，可能重训、消耗显存和创建新制品。这是**读/算语义缺陷兼性能瓶颈**。

建议明确拆开：读取已有 runId/snapshot 的结果不执行任何节点；没有结果时要求显式 run，不能隐式重算。保留一次随机运行的不可变结果供读取，不等于允许将随机节点缓存给另一次新运行；R6.4 仍完整保留。

### B5：实时画布“run 成功”不等于求值完成

文档原文，架构 §7.1：

> “`run(scope)` / `status()` / `cancel()`……与 UI 走同一个 Runtime。”

源码：`liveCanvasBridge.ts:259` 调用 `runWorkflow()` 后查看 runtime；当前 `useWorkflowStore.ts:990` 的运行按钮主要登记已有真实资产，自动求值由 `graphRunner` 另走 300 ms 防抖。实时返回的 pending 只检查 computing，可能漏掉尚在防抖、待执行、手动触发、blocked 的节点；错误节点也不必然使顶层 ok=false。

这是源码确认的完成判据缺口，尚未用真实页面量化。两次动画帧或截图不能代替求值屏障。尤其 `train.function` 的手动执行应继续由原有显式触发语义控制，不得为了让 run 看起来完成而自动启动全部训练。

建议 run 返回具体任务身份，状态绑定请求时的执行作用域、节点输入指纹和输出版本；只有对应求值终态、错误/阻断状态已收齐，才能宣布完成。图变了，要标记该运行与当前图的关系。截图只证明页面像素，数值正确性另由输出证据确认。

### B6：文档陈旧导致 agent 花时间修复文档造成的问题

| 原文位置 | 原文/现象 | 当前事实与修订方式 |
|---|---|---|
| docs/README.md 文档索引 | MCP“未实现” | 实际已有15工具；改现行状态，历史记录不回写 |
| MCP 设计 §6.1 | 28 算子分布，custom.model 为 simulated | 当前 catalog 为16算子，不能再按旧表选算子 |
| MCP 设计 §6.3 | 数据源“每个数值列各自还是一个端口” | 现行契约只有 `__table__`，显式经 `data.columns` 拆列 |
| MCP 设计 §6.5 | 自定义模型“必须提供 build_model” | 现行规范推荐 `class Model(nn.Module)`，兼容 hooks 是另一层接管 |
| MCP 设计 §6.2 / §9 G-1 | 没有新建工程；制品以指纹前16位为目录 | 已有 sciviz_new；现行制品用唯一 artifact_id，旧表会误导操作 |
| MCP 设计 §9 G-5 | 训练→留出集评估“不成立” | 已有 model.predict，与该文自己 §6.5 也冲突 |
| MCP 设计 §8 | node 直接运行 `.mjs`，声称动态 import 已自带加载 | runCli 没有自己注册 tsx；相对 TS import 解析依赖运行时/loader，接入必须对真实启动环境验证 |
| MCP 设计 §3.3 / §5 | 串行防覆盖；进度在stderr | 缺项目锁/写入身份；JSON 模式进度回调被抑制，MCP客户端收不到过程状态 |
| 架构 §4.3 / §7 与 Agent 设计早期现状 | 零持久化、CLI或Agent面缺失 | 后文已有完成记录；应把初始审查明确标为历史基线 |
| AGENTS.md R1 | ENGINE_NODES 白名单仍作现存债 | 架构已记删除；规则应保留，现存债清单须单独对齐 |

Agent 设计的盲测仍保留已移除的分帧/特征类流程，验收样例要改为当前可用算子，验收的“读→写→判→跑→取数→纠错→撤销”能力不变。对话栏也累积多次权限更正；外部 MCP 不应被迫阅读全部历史补丁才能知道当前能力。

建议将“现行规范、可执行示例、历史原因”分开组织。工具数、参数、能力、端口、错误码通过注册表/实际工具声明校验；现行文档优先链接唯一规范，不再手抄清单。固定的参数示例必须通过 smoke/盲测。`initialize` 当前没有返回文档所设想的 server instructions，需补一段短的现行指引，不能依赖客户端自动读整个仓库。

### B7–B10：次级结构瓶颈

- **全局串行。** MCP `queue` 串行所有工具，训练会堵住其它工程和纯读工具。`_meta.durationMs` 从出队后开始，漏报排队耗时。宿主每会话也有计算锁；开多个连接并不意味着 GPU 可以无限并行。
- **模型每次承担机械衔接。** 读结构→读契约→干跑→应用→读新指纹→校验→运行→读输出→写报告，很多步骤没有新的科学决策，却各占一次模型回合。patch 已支持一批 op，但响应没返回新 editFingerprint，促使模型为下次写入再 inspect。其 validation 已在响应里，反复单独 validate 可能是同一基线重复验证。
- **结果信息不足又过大。** 图分页先全图投影再 slice，默认10节点/页；每次重新解析图与历史清单。`inspectablePorts` 的投影没有保留所有 metrics/meta/artifacts/cache 信息，节点 inspect 不能替代 run 输出的全部事实。最近运行查找还会按工作流名称匹配，未强制验证 projectId、图和数据身份，存在旧结果误绑定风险。
- **截图成本与视觉回合。** new/patch/undo/run 默认截图；递归复制每个元素所有计算样式，成本随 DOM 增长。图像要编码、搬运，模型也要读图。无头捕标准图每次启动本机 Chromium，虽然一次运行内已有复用，跨运行没有复用。未知具体成本，先按需关闭再埋点。
- **大型文本分页。** read 只有行数上限，底层每页扫描整文件计算摘要；单行非常长时仍可能超过 MCP 字节预算。多页之间没有绑定文件快照，文件变化会拼接不同版本。
- **跨进程临时文件。** 请求号从1开始，多个 MCP 进程共享 `.tmp/mcp` 文件名可能冲突，既是额外 I/O，也有错误归属风险。改为每进程/会话唯一目录，或类型化参数直接进入 Facade。

## 5. 完整目标方案

### 5.1 原则与架构边界

继续以 IR、契约、补丁核、求值核为唯一事实来源。**薄壳的本质是“不拥有业务语义”，并不意味着必须把类型化数据变成 argv 再变回 JSON。**

目标结构：

```text
CLI（参数解析/展示）     MCP（协议/结果包装）     UI/Chat（交互/授权）
          \                  |                  /
            同一个类型化 Facade / 用例执行服务
              |            |             |
         工程快照与写入   运行任务与取证   注册表与有界批量请求
              \            |             /
                  原有 Contract / Kernel
                            |
                原有宿主 / Pyodide 适配器
```

这需要在实施前修订 MCP 的 M1 导入白名单和静态检查：允许唯一 Facade 入口，仍禁止壳 import plan/validate/算子并自己做判定。M2 要允许**通用组合用例**在 CLI 与 MCP 同步登记，禁止隐藏训练流程的 M3 保持。新模块导出、CLI/wire/文件字段和错误码都先按 R3 登记，再改代码。

### 5.2 工程会话与快照

一次发现响应提供：状态来源（file/live）、明确工程/页面身份、editFingerprint、持久化状态、图骨架、数据身份、当前错误、可用能力和最近运行的匹配关系。文件侧再提供完整文件 SHA-256，区别于只覆盖可编辑图的 editFingerprint。

随后按 nodeId+groupPath 精确取目标节点、邻域、代码或输出，不默认全图详细分页。大图保留完整轻量骨架和按需详情；修改源码/块内代码前，仍必须读到完整原文且确认摘要没变。

只读 cursor 绑定快照摘要。工程在分页过程中变化时，要拒绝续接或继续明确读取旧快照，不能无提示混入新状态。实时动作绑定 pageId/projectId；不能每次仅按当前焦点重选，从而把上一页的补丁发到另一页。

### 5.3 结果读取与执行分离

运行由 Facade 持有 RunContext：工程/计算基线、数据身份、宿主会话、执行状态与输出引用。run 返回 runId / 结果句柄；inspect 对该句柄只读，不隐式执行。

渐进实现：

1. **短期少改动。** 将当前已有 `RunOptions.heads[]` 暴露为类型化的运行取证选项：同一次运行同时取需要的多个节点/端口和有限行，避免为了报告再跑一次。CLI 与 MCP 同步映射，不能只在壳里加私有逻辑。
2. **会话内快照。** 完成后保留有界时长的引擎会话或隔离结果快照；多页读取固定 runId/输出版本。需要计算新图时另分配运行上下文，不能让新求值覆盖旧运行的数据句柄。
3. **持久化取证。** 对需跨会话带走的证据保存声明过的表/有限预览与图像制品，登记身份、schema、摘要和资源上限。只保存摘要就不能承诺恢复完整行值；全表持久化需要明确磁盘和格式成本。

过期句柄、宿主重启、未物化行值明确失败，提示显式重新运行。随机节点的结果快照可以多次读取，但发起新 run 仍按原 determinism 规则，不用旧随机结果充当新计算。

### 5.4 长任务、完成屏障与取消

执行请求快速返回 taskId，后续 status/wait/cancel 在控制通道工作；同步短任务兼容保留。wait 优先长轮询/状态事件，避免每秒让模型决定“再查一次”。支持 progressToken 的客户端接进度通知，不支持者读取同一个 task 状态。

状态至少区分 accepted/queued/running/done/partial/failed/cancel-requested/cancelled，并携带请求作用域、节点终态、证据位置。取消先请求适配器，在真正的中断点生效后才宣布 cancelled。宿主已有 cancelNode 可以复用，但无头 Facade 的任务生命周期与连接保留需要补齐，不能只加一个外表 cancel 工具。

实时画布同样以求值计划和所需输出的新鲜度为完成屏障；部分图未接完仍可以编辑，执行范围内的问题要如实报告。用户未授权自动训练的手动节点保持原边界。

### 5.5 并发：按资源调度，别按协议一刀切

先移除全局 stdout 副作用，再实施：

| 请求类型 | 调度规则 |
|---|---|
| catalog/explain 与不可变运行结果读取 | 有界并发，无需排在训练后 |
| 工程结构读取 | 基于一致快照；避免读到半写文件 |
| 同工程 patch/undo/report/save | 共同工程写入锁；验证图基线与完整文件基线 |
| 不同工程写入 | 可并发，统一路径身份和资源限制 |
| 同引擎会话计算与取值 | 保持现有协议帧与会话锁语义 |
| GPU训练 | 宿主资源队列；4GB设备默认保守限制并行度 |
| status/cancel/心跳 | 控制路径不等待长计算锁 |

锁必须处理多 MCP 进程和 UI 写入，不能只是当前进程的 Map。浏览器 File System Access 直接写文件绕过宿主锁，因此统一写入代理/共同锁协议是完整目标；过渡期明确文件模式与实时模式的写入归属，并检查磁盘摘要。对于不遵守锁的外部编辑器，不能声称应用内锁提供绝对排他。

补丁“业务原子性”不等于磁盘提交原子性。文件写入用临时文件+原子替换、提交前基线复核；图没变但报告变了时，基于最新完整工程合并图补丁，不能用旧内存对象覆盖新报告。冲突明确拒绝，不自动强覆盖。

### 5.6 降低模型回合：批量读与通用执行组合

首先让一个响应把下一步会用到的信息带齐：patch 返回新基线、变更摘要、同一基线上的 validation；run 返回所请求的指标、有限行、cache/simulated/身份事实和证据引用；失败返回具体 code、opIndex、node/port、来自唯一错误表的修复动作及是否可重试。

其次增加**有边界的批量读取**：一次请求几个节点/端口/小段代码，每项结构化结果独立，整体有字节与数量预算。不会因为批量而默认读取全部行值、代码或图像。

最后增加通用组合用例，概念上可表达“应用明确 ops→执行指定范围→读取明确输出”。请求必须显式列步骤、输入、停止条件和结果选择；步骤间允许有限的类型化输出引用。服务只执行既有用例，不自主选择模型、研究步骤、拆分方法或端口名，不支持 shell/任意脚本。

这区别于文档禁止的 build_training_pipeline：**机械衔接可以委托，科学决策不能藏起来。** 组合用例在 Facade 中实现、CLI 与 MCP 同时登记，所有子步骤有独立审计与结果。不要以纯提示词暗示 agent 自动合并所有动作。

事务边界必须讲清：一批图 ops 可以原子；“图改动+小时级训练+报告”不能承诺整体回滚。patch 成功而运行失败时记录部分完成，保留可撤销补丁；取消不能撤销已经产生的模型制品。通用组合默认在需判断的新信息、基线冲突、权限等待或执行失败处停下，把证据交回模型。

给写请求和组合步骤增加稳定 requestId/idempotencyKey：重试同一已提交请求返回原结果；请求内容不同但 key 相同拒绝。没有幂等记录时，对写操作超时不能直接重发，先核对是否已提交。

### 5.7 数据、缓存与输出预算

- 先记各阶段耗时，再优化 CSV 解析结果和内容哈希复用。缓存身份必须包含真实内容与解析/视图版本；仅依赖路径、mtime、文件大小会漏掉同尺寸同时间戳内容变化，只能作快速线索，不能成为科学身份。
- 复用宿主内已装数据时，必须核对内容身份和会话 generation；宿主重启后重新装载。现有 wire 没有这项握手就先登记，不在 MCP 私下跳上传。
- 编译部署的 CLI/Facade 或按命令延迟加载可减少首次约1秒装载；已有 TS import 缓存让热调用毫秒级，所以其优先级低于多轮模型和重复运行。
- 默认紧凑摘要，科学指标不裁掉；代码、完整参数、大表和图像按需取。分页同时受字节数与行/节点数限制，返回明确完整性与下一页位置。
- 图补丁过程中 `includeScreenshot=false`，在阶段结束或视觉任务时取一次图。图像绑定 runId/指纹与参数；按需捕获具体节点，避免 includeFigures 一次搬全部20张。
- 图像渲染服务可有界复用 Chromium；异常重建并在空闲时释放，不无限持有浏览器。进程缓存留在 Facade/渲染适配器，不放 MCP handler。
- 增量图查询或注册表目录缓存以契约版本/实现摘要失效；实现变了、宿主换了不能继续展示陈旧能力。

### 5.8 协议实现的选择

保留 stdio。协议版本协商、输入校验、进度、取消、资源分页与控制消息需要形成完整实现；当前固定返回协议版本且仅处理少数方法，已经暴露控制通道缺陷。可以评估受维护的 MCP SDK，但它是协议可靠性选择，**不是毫秒级传输加速承诺**。

SDK 若采用，应读取同一个 ToolSpec/schema，锁依赖与版本，不重新声明算子/补丁字段。若继续手写，则补协议矩阵、真实客户端兼容与异常测试。两条路线都必须修请求局部 I/O；换 SDK 本身不会自动修掉业务误重算。

## 7. 如何确保加速后的完成质量

### 7.1 必须守住的规则

1. 不能用“工具调用成功”代替“业务运行成功”。保留现行退出码1的可诊断负载，并在 envelope 明确业务状态。
2. 图写保留基线、op级校验、审计与反向动作；已有未接完子图不阻断正常编辑。
3. 结果必须绑定项目、运行、数据、输入指纹/输出版本；历史结果明确历史，不能与当前图混用。
4. 随机/volatile 结果不充当新运行缓存；确定性算子仍按唯一规则缓存。
5. 图像只作视觉证据，数值须对输出或独立真值；UI/e2e、纯逻辑测试、宿主测试、算子验真各守原分工。
6. 多页代码修改前完整读取且基线一致；精简传输不能把未读完当读完。
7. 组合工具保留每步结果，失败或取消后准确说明哪些已经落地；报告数字有真实工具/run证据。
8. 高权限、批量和异步不自动放开源码写、路径、训练触发或数据外发范围；保持用户已有授权边界，不额外制造逐次确认。

### 7.2 针对性回归

| 场景 | 必须验证 |
|---|---|
| 慢工具 + ping/tools/list | 所有RPC独立正确回包；工具JSON不被控制消息污染 |
| catalog / 长代码 / 大图 | 大小边界上仍是合法JSON；cursor能读全；多字节字符不损坏 |
| 同一随机运行多页 | runId、输出身份相同；读页无evalNode；与该运行独立记录吻合 |
| 同名工程 / 嵌套同名节点 | projectId/pageId/groupPath精确寻址，不按名字悄悄取别处结果 |
| patch后立即run/截图 | 等正确计算基线的终态；旧图、新图与手动训练状态明确 |
| 两进程patch、patch与report并发 | 一方冲突或合法合并，无覆盖未参与改动的字段 |
| 写入已提交但客户端超时 | 同idempotencyKey只提交一次；同key不同内容拒绝 |
| 长训练cancel/页面断开 | 控制请求及时接受；真实cancel后才标结束，无孤儿计算 |
| 数据同尺寸替换 / 宿主重启 | 缓存和装载身份失效；新鲜结果不可假装复用 |
| patch成功、run失败、报告未保存 | 明确部分成功、可撤销范围，不能宣布目标已完成 |

扩展现有 smoke 为“真实stdio上的协议与闭环回归”，现有静态检查仅保分层。涉及画布桥时加真实浏览器测试；涉及宿主加 `.venv` unittest；算子本身未变时不为凑验收去跑所有训练或改真值。若后续修改算子，按仓库要求更新哈希、重启两侧并跑覆盖该算子的独立真值。

### 7.3 性能与质量联合验收

建立四类任务：小图参数修改、嵌套代码修改、运行后多节点/多页取证、训练与带图报告。每类固定工程、数据和完成判据，分别量冷/热、多次重复、统计中位数与p95。外部agent试验固定客户端、模型和提示词版本，保留工具轨迹，失败任务必须计入。

采集：整任务墙钟、模型决定次数、实际模型输入/输出token（客户端可提供时）、工具排队/装载/数据准备/计算/取证/包装耗时、payload/image字节、evalNode次数、数据上传量、cache命中、重试、人工等待和成功完成率。服务器不能凭自己的毫秒计时反推模型耗时。

建议验收目标（目标值，尚未达到）：

- 合法schema调用的用法错误、隐式重算、无声截断、错误项目结果绑定归零于覆盖的回归集。
- 同一已完成run分页新增计算次数为0；写请求重复提交次数为0。
- 标准短任务模型往返比基线减少至少40%；证据与报告完成率不下降。
- 热的轻量工具服务侧p95先设100 ms以内；长任务期间status/cancel接受请求p95先设500 ms以内。取消真正完成耗时另算，因为是协作式中断。
- 总体加速倍数用实测报告。若任务以训练为主，不承诺减少不可省的训练时间；应证明没有重复训练且等待状态可见。

上线逐片验证：先保持当前串行执行并修局部I/O，再开放纯读并发，再引入会话结果与组合请求。保留老CLI形式与明确版本迁移，避免一次升级使外部客户端全部失效。

## 8. 当前版本可以立即采用的操作习惯

无需产品改动即可减少一些耗时，但不能完全消除上述缺陷：

- 一项任务选定文件或实时画布来源；不混用两者验证同一补丁。
- 已知图修改用一批明确id的ops，不逐块逐线调用；代码变动复杂或影响未知时保留预演。
- 利用patch响应已有的validation、run响应已有的输出和指标；只有工程状态/数据绑定/判据变了才再校验同一事项。
- 文件inspect看摘要/代码时尽量精确到节点；整图分页可用现有limit=25。代码仍读到codeComplete=true，不能为快省略修改前原文。
- **对行值尤其训练图，避免反复inspect(rows)。当前版本会重算。** 必须取多页时明确它们属于不同run，不能拼成同一次实验；重要取证应先实施运行快照修复。
- 实时patch/undo/run的includeScreenshot可明确设为false，阶段结束再screenshot；需要视觉校验的任务仍取图。
- run不需要图像时保持includeFigures关闭；已经捕获的图用inspect_figure读，不为了看图重新run。
- doctor是完整体检，稳定环境不必每步都问；宿主/地址/能力改变或报环境错时再查，不能仅省去体检而假设GPU和新算子存在。
- 当前catalog.type/schema/JSON过滤、validate.file schema等缺陷不能靠“照说明正确调用”解决；先修接口，别把失败归给agent能力。

## 9. 最终推荐

保留 MCP、CLI、画布共用的契约和核。第一批修 schema、stdout、截断、文档和运行完成语义；第二批让一次运行的结果可反复读、长任务可等待和取消；第三批把明确的机械步骤批量交给同一个Facade执行。每批以真实结果身份、独立验证、并发与幂等回归为质量闸门。

真正的加速单位是**“完成一个用户目标所需的关键路径”**。只盯单个MCP调用的毫秒，会优化掉最小的一块，留下反复模型决定、重复运行和错误恢复这些大成本。
