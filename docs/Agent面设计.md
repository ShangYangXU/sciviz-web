# Agent 面设计 v0.1

> 状态：草案（设计基线）
> 日期：2026-09-12
> 上位：[架构总纲](./架构总纲.md) §2 / §7.1 / §9 / §10-P3 ｜ [数据契约规格](./数据契约规格.md) §4.3 / §8
> 作用：把"agent 是本项目的一等使用者"从一句定位，落成一组**入口**、一种**闭环**、一条**增量落地路径**和一条**验收判据**

---

## 0. 一句话

**不是"一半给人用、一半给 agent 用"，而是同一个核、两种入口。**

"双向"最自然的误读是把项目切成两半：给人一套功能，给 agent 另做一套。这个切法在本项目的历史上已经出现过一次，代价写在架构总纲 A5 与契约规格 R6.2 里：真引擎一条路、`executor.ts` 一条路，分界是硬编码白名单 `ENGINE_NODES`，结果是"同一件事有两处真相，漏改一处就静默出错"。

所以本文档的第一原则，与架构总纲 §0 同源：

> 判断某个 agent 抓手是否合格，只问一句：
> **它是否让 agent 在不读源码、不点鼠标的前提下，独立走完"读懂 → 改动 → 运行 → 取数 → 定位错误 → 汇报"这一整圈？**

六个动作缺一个，抓手就不成立：能读不能改，是只读文档；能改不能跑，是把风险留给人；能跑不能取数，等于没跑；取不了数就定不了位，定位不了就汇报不出可信结论。

## 1. 范围

**本文件定义**：agent 面的入口形态、动作空间、证据格式、汇报格式、验收方式、落地顺序。

**本文件不定义**：契约规则本身（见[数据契约规格](./数据契约规格.md)）、端口的类型语义（同上 §4）、画布交互（见 `sciviz-web/docs/`）。

## 2. 现状审查：agent 今天到底能抓住什么

结论先给：**算子级可操作，图级不可操作。** agent 今天能把一个算子算出来，但没法表达、校验、运行、检查"一张图"。

| 现存物 | 实际能做什么 | 层级 | 对 agent 的价值 |
|---|---|---|---|
| `sciviz-local` 的 `WS /engine` | 装数据、`evalNode`、`head`、`dropNode` | 适配器层 | **可用但太低**：agent 得自己扮演调度器，且没有图的概念 |
| `GET /health` | 报后端 / 设备 / 算子清单 | 适配器层 | 可用，是"自描述"的现成样板 |
| `src/engine/plan.ts` | 纯函数：算谁该重算、缺什么输入 | 契约层 | **可用**，已能被 `node --test` 直接跑，是无头核的种子 |
| `src/workflow/yaml.ts` | 图 ↔ 文本往返，含数据集身份认回 | 序列化层 | 可用，但内容不足以复现（R10 的差异清单） |
| `scripts/verify-operator-truth.mjs` | 独立扫 CSV / 独立 DFT，给出**与引擎无关**的真值 | 验证层 | **最有价值的一个**：它能回答"算对了"而不只是"跑通了" |
| `scripts/e2e.mjs`（78 KB） | 驱动 DOM：拖拽、拉线、点按钮、读探针 | 界面层 | 现状下**唯一能端到端验证行为的抓手**，但层级错了；输出是散文，不是证据 |
| `scripts/debug-module.mjs`、`tmp-repro.mjs` | 一次性复现，注释写明"用完即删" | 界面层 | 已经腐化：脚本还在树里，问题早就不在 |
| `src/**/*.test.ts`（`node --test`） | 纯逻辑单测 | 契约层 | 可用，但那是**测试**不是**操作面**：能证明逻辑对，不能操作产品 |

三条判断：

1. **唯一的图级入口是"驱动浏览器界面"。** 这是今天事实上的 agent 抓手，也是不该有的那个：它把 agent 的能力上限锁在 DOM 选择器上，且每次界面改版都要连带重写验证脚本（`e2e.mjs` 的体积就是证据）。
2. **唯一健康的抓手是独立真值**，而它现在只是一个孤立的、写死列名与窗长的脚本。它代表的模式应该被制度化：**每个算子都能被独立验真**。
3. **没有任何一处让 agent 读懂"这个项目现在是什么状态"。** 校验结果、节点状态、错误码、产物身份、缓存命中、模拟标记，全部只以人能读的形式存在于界面上。

## 3. 五个架构阻塞

在动手做抓手之前，有五件事必须先在架构上承认。它们不是"实现细节"，每一个都会让 agent 面直接失真。

### B1 "运行"有两个含义，agent 一定会踩

同一份代码里，"跑一遍"指向两件不同的事：

- **实时重算**：编辑即触发，防抖 300 ms，`plan.ts` → `evalNode`，真算。（`src/engine/graphRunner.ts`）
- **点「运行」**：走 `executor.ts`，按 `mockDurationMs` 睡时间、吐资产卡片，**是模拟**。且它刻意**跳过**所有引擎能实时算的节点（`runNodes` 里的 `isEngineNode` 过滤）。

后果：agent 收到"把这张图跑一遍"，点下去会得到一批模拟资产；而这批资产**不是图的结果**，只是图上那些还没接进引擎的节点的占位产物。一个以"可复现"为价值主张的工具，不能有一个语义随节点类型变化的"运行"。

归属：P1（统一 Job 模型 + `executor.ts` 降级为模拟适配器）。

### B2 编排绑在浏览器 store 上

`src/engine/graphRunner.ts` 直接 `import` 了 `useWorkflowStore`、`useNodeOutputStore`、`useDataStore`，并通过 `backend.ts` 选址（其中一条判据是 `localStorage`）。也就是说：**"算出这张图"这件事今天只能在浏览器主线程里发生。**

后果：无头运行不存在，CLI 无从写起，agent 只能退回驱动 DOM。

归属：P1。这也是把 P2 的 CLI 变成可能的那个前置动作。

### B3 零持久化、无运行清单

全仓库没有工程文件、没有 IndexedDB、没有运行记录落盘。`Run` 只在内存里（`useWorkflowStore.runs`），`Run.logs` / `assets` / `durations` 只被人读组件消费。

后果："汇报"没有载体。agent 跑完一次，除了 stdout 什么都留不下；更做不了契约规格 §7 的 L3（本次与上次对比、检测漂移）——而那正是"复现"能不能被证明的关键。

归属：P1（持久化）+ P2（`.sciviz` 工程文件与运行清单）。

### B4 数据供给在浏览器列式存储里

数据集在浏览器侧（`src/data/columnStore.ts`）以 `Float32Array` 存在内存里，只把**启用的数值列**通过二进制帧送进执行引擎。本地宿主自己不读 CSV。

后果：即使 B2 解决了，无头进程也拿不到数据。agent 必须先有"把一份 CSV 变成 `DatasetRef`"的能力，这一段今天与浏览器耦合。

归属：P1–P2。注意契约规格 R3.2：数据集身份必须是**内容哈希**，而当前 `graphRunner.datasetSignature` 只算 `行数 | 时间列 | 启用列名`——两份列名列数相同、内容不同的 CSV 会被判为同一份数据。这个缺陷在无头场景下会更危险，因为 agent 会真的去换数据。

### B5 算子有两处真相

`ENGINE_NODES` 白名单（`src/engine/plan.ts`）与算子注册表（`src/workflow/nodeRegistry.ts`）是两处清单。新增算子必须同时改两处，漏改则"看起来能跑、其实不走真引擎"且不报错。

后果：一个不知道这件事的 agent 会写出静默失效的图，并且**它会如实汇报"跑通了"**。

归属：P0–P1（Manifest 是能力的唯一声明处，白名单消失）。

> **已收（2026-09-13）**：白名单已删除。每个算子在 `NodeTypeDef` 里用必填的 `execClass` 声明归谁算，`isEngineNode` 与 `catalog --json` 的 `runtime` 都读这一处；新增算子漏写编译不过。"写图的人不知道判据"这条保留价值的地方只剩 `execClass` 的语义本身（见[接口文档](./接口文档.md) §7 变更记录）。

## 4. 定义：一个核，多个壳

```
L5  Clients    画布 UI  ｜  agent 工具面  ｜  界面对话栏  ｜  CI
                      ↓ 三者只通过同一组动词调用
L4  Facade     catalog ｜ validate ｜ patch ｜ run ｜ inspect ｜ explain ｜ report
                      ↓
L3  Runtime    Job 模型、调度、缓存、RunManifest      ← 从 graphRunner 抽出来，去掉 store 依赖
                      ↓ 通过适配器接口
L2  Adapters   pyodide-worker ｜ local-process ｜ simulated
                      ↓
L1  Contract   端口类型、L1 校验器、错误码、指纹
                      ↓
L0  Core IR    Project = 图 + 数据引用 + 环境锁 + 运行记录
```

对应到架构总纲 §9 的目标目录，agent 面 = `packages/agent-api`（Facade，契约与动作）+ `packages/cli`（外壳）。**不需要新发明一层**，需要的是把 Facade 从"设计要点"变成"被三个客户端真的共用的东西"。

三条依赖规则（比 §2 的 R-A/R-B/R-C 更针对 agent 面）：

| # | 规则 | 为什么 |
|---|---|---|
| RA-1 | Facade 是**唯一**动作入口；UI、agent、CI 都不得绕过它直接改图 | 绕过一次，就有一份改动不进审计、不过校验 |
| RA-2 | Facade 与 Runtime 不得依赖 DOM / React / store / Worker / Pyodide | 否则无头运行不成立，P2 的 CLI 与 P3 的 agent 面同时落空 |
| RA-3 | agent 的动作空间是**图的补丁**，不是任意代码 | 边界约束、增量重算、逐边验证、有界动作空间是本项目相对"直接写脚本"的全部立足点（架构总纲 §7.1） |

RA-3 有一个容易搞错的地方，先在这里划清：**`custom.script` 节点内部仍然是任意 Python**（契约规格 P1：自由在节点内部）。被约束的是**图这一层**——agent 不能凭空注入一个不在算子清单里的新算子，不能绕过端口类型拉线。所以 Python 报错时那份完整 traceback 恰恰是 agent 面里最需要结构化输出的东西。

## 5. 十一个抓手

按"读 / 写 / 跑 / 看 / 报 / 验"六组给出。命名以 CLI 动词为准，其他壳（MCP、HTTP）只是同一个动词的另一种传输。

### 读 —— 先用契约理解工作流，项目源码按需开放

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G1 | `sciviz catalog --json` | 无 → IR 的 JSON Schema + 算子清单 + 错误码表 | **自描述**。算子清单含 id / version / implementationHash / 端口描述符 / 参数 schema / 执行等级 / 确定性等级。agent 由此知道"有哪些算子、怎么接、什么算错" |
| G2 | `sciviz open <project>` | 工程文件 → 图摘要（节点、**解析后的端口**、连线、指纹、校验态、数据身份） | 端口必须是解析后的实际列表，不能只给静态注册表——数据源与函数节点的端口是动态的 |

G1 保证 agent 搭建和校验工作流时优先使用唯一契约，不靠猜算子实现。需要排查或修改项目本身时，另有 CLI-11：它可在工作区安全文本中 `list/search/read`，并运行登记的检查、计划与应用源码补丁。修改已有 Markdown 时必须完整读取并在原路径上计划差异；新建文件只用于用户明确要求新建的情形。完全访问权限档允许工作区内 `.md` 文档写入，但不放宽路径围栏，也不允许源码写入；这条能力不替代 `catalog`、契约和执行证据。

### 写 —— 有界、原子、可回滚

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G3 | `sciviz patch <project> --ops ops.json [--dry-run]` | 一组补丁 → `{applied, rejected, diff, validation, projectHash}` | 原子（要么全过要么全不动）；被拒的 op 必须带错误码；`--dry-run` 只回校验结果 |
| G4 | `sciviz validate <project>` | 工程文件 → L1 结果列表 | 稳定错误码 + `nodeId`/`portId`/期望/实际。退出码区分：契约违约（可修）与用法错误（调用方写错） |

**动作空间几乎不用新设计**，它就是 `useWorkflowStore` 现有动作的序列化形式，再加上数据动作：

```
addNode / removeNode / renameNode / moveNode
connect / disconnect / setParam / resetParams
setWorkflowName / setDescription
setDatasetFeatures / setTimeColumn / importDataset
```

这个镜像关系是**刻意的**：图上的每一个动作，人和 agent 走的是同一个函数。也因此，"agent 的改动在界面上可见、且可回滚"不是额外功能，而是这条规定的自然结果。

### 跑 —— 与界面同一条执行路径

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G5 | `sciviz plan <project> [--json]` | 工程文件 → 求值计划（要算什么、为什么、跳过什么、为什么） | 就是 `planEvaluation` 的输出，含 `evaluate` / `unchanged` / `blocked` / `missing` / `manual` 及各自原因 |
| G6 | `sciviz run <project> [--nodes ...] [--json] [--out DIR]`，配 `status` / `cancel` | 工程文件 → `run.json` + `report.md`，进度以 NDJSON 流式输出 | 与 UI **同一个 Runtime**。执行等级（interactive / background / batch）是 Job 的属性，不是两条代码路径 |

G5 单独列出，是因为它是 agent 最便宜的一次自检：不花算力就能知道"我要做的事会不会被拦住、上游缺什么"。它也是把"为什么没重算"变成可回答问题的唯一办法。

### 看 —— 结构化证据，而不是散文

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G7 | `sciviz inspect <project> [--node N] [--port P] [--rows 20] [--from latest]` | → 先发现全部实际输出，再按节点/端口取得与探针同源的值摘要 | 不指定节点时列出全部节点与实际端口；JSON 含摘要、可取数端口、复用状态、指纹、算子事实、元信息、制品与错误。`--rows` 只在唯一表端口时自动选择，多候选必须显式指定；完整血缘未落地时如实列为缺口 |
| G8 | `sciviz explain <E_CODE> [--context ...]` | 错误码 + 上下文 → 原因 + 修复建议 + 哪个 op 能修 | 错误码表即文档。这是"自己调试"闭环的合拢处 |

G7 里的证据字段是重点，不是装饰：

- `cache: hit` 告诉你"这是复用还是新算的"——否则 agent 无法区分"没算"和"算了但一样"；
- `simulated: true` 告诉你"这个数不是算出来的"。契约规格 R6.2 要求它必须显式；
- `fingerprint` 先回答"是不是同一份计算"；完整 `lineage` 才能回答"这个数字从哪一步来"。当前前者已可查，后者尚未落地，必须显式列为缺口，不能用推测值填充。

**调试闭环因此是五步**：`validate` 出错码 → `explain` 要建议 → `patch` 修 → `validate` 复验 → `run` 重算。这五步里每一步都不需要人，也不需要 DOM。

### 报 —— 事实与叙述分开

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G9 | 运行目录（`run` 的产物） | `runs/<runId>/run.json`、`report.md`、`patch.diff`，加 `runs/index.json` | 见 §7 |
| G10 | `sciviz doctor` | 无 → 环境自检 | 适配器可用性、设备、**算子清单差异（声明的 vs 可用的）**、数据集可解析性、工程记录的版本 vs 当前版本 |

G10 存在的理由是 B5 的反面：当"这个节点在浏览器里跑不了"（开发日志记的第二个契约缺口）成为事实时，系统必须能如实说出来，而不是让 agent 猜为什么结果不对。

### 5.1 Chat 的长程任务闭环

对用户要求“自主修改、实验验证、比较效果并写报告”的多阶段目标，Agent 需要显式维护一个可恢复的计划，而不能把一次 provider 工具循环当成任务边界。Chat 的 `task_checkpoint` 用现有会话日志保存目标、步骤、完成判据、状态、证据引用和最终报告；实验实际仍只经本章已有抓手执行：读图 / catalog → 规划与校验 → 补丁写入 → 运行 → inspect / verify → 按证据比较 → 报告。

步骤完成必须引用一个成功的工具结果 `callId`。模型可以根据运行结果追加或调整未来步骤，但不得抹去已完成步骤的证据。报告事实来自工具结果与 `run.json`；叙述先给结论，再按用户目标与证据需要简短交代基线、修改、条件、观察和限制。当前工程现状只作背景，不重复盘点；无法比较时如实写明。修订项目已有报告须保留同一报告身份并按版本基线更新，不能另建报告替代。计划跨消息保存，因此达到本轮额度后可以续跑；刷新只恢复进度，不在没有用户触发时后台继续请求模型。此任务计划属于 L5 对话编排，不取代 L3 Job、运行清单或契约层。

2026-09-26 将长程任务的报告交付补为项目级：同一次用户发起可在前台自动续接有限窗口，结束/受阻/等待用户/停止后不再自行发起；续做始终重读当前工程。任务报告进入 `.sciviz` 顶层 `reports:`，在本地报告管理页渲染 Markdown；图像从最新画布结果在本机捕获并内嵌，来源与摘要随报告保存。会话检查点保留任务轨迹，项目报告保留可带走的交付物，两者通过 `taskId` 关联；机器事实仍以 `run.json` 为准。

设计参考：[AI Scientist](https://github.com/SakanaAI/AI-Scientist/blob/main/ai_scientist/perform_experiments.py) 把运行次数设上限、保存每轮代码快照，并将成功指标或错误回注给模型以调整后续实验；[Agent Laboratory](https://github.com/SamuelSchmidgall/AgentLaboratory) 将调研、实验、写作分成阶段；[mini-SWE-agent](https://github.com/SWE-agent/mini-swe-agent/blob/main/src/minisweagent/agents/default.py) 展示了带步数 / 成本 / 时间边界、持续保存轨迹的紧凑执行循环。SciViz 采用分阶段、证据回流和边界控制这些模式，执行仍绑定自己的图补丁与运行契约。

### 验 —— 区分"跑通了"与"算对了"

| # | 抓手 | 输入 → 输出 | 关键要求 |
|---|---|---|---|
| G11 | `sciviz verify --operator <id>`（或 `--all`） | → 每个算子的独立真值比对结果 | 真值来自**独立实现**（独立扫 CSV、独立 DFT），不许抄引擎的输出 |

这一条是本项目特有的，也是最容易被忽略的。`verify-operator-truth.mjs` 的注释已经把道理写清楚了：把引擎的输出抄一遍只能证明"它和上次跑得一样"，证明不了"它算对了"。对一个以正确性立身的工具，agent 必须能回答第二个问题——否则它会忠实地汇报一个错的数。

实现上它不必是新机制：把现有的独立真值脚本泛化成**注册式真值夹具**（每个算子一份 fixture + 一段独立算法），`verify` 只是跑它们并汇总。当前 23 个内置算子只覆盖了 2 个，这个缺口值得单独列为一项工作。

## 6. 入口形态：文件 + CLI 先行，MCP 靠后

三种候选形态的取舍：

| 形态 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **文件 + 命令行** | agent 最稳的原语；天然可 diff、可 git、可审计；与"工程文件是唯一真相载体"（架构总纲 §8）同构；不需要新服务 | 交互式探索不如 API 顺手 | **先做这个** |
| 本地 HTTP / WS 工具面 | 有状态、可流式、浏览器同样能连 | 要定义会话与认证边界；宿主目前只监听回环且执行任意 Python，**不可暴露**（`sciviz-local/README.md` 已明说） | 等 Facade 稳定后再加，作为同一动词的另一种传输 |
| MCP 工具面 | 与 agent 运行时的集成最省事 | 最容易把编排逻辑写进 tool handler，形成**第二套真相** | **最后做**，且只做薄壳 |

顺序不能颠倒的理由只有一条：MCP 先行会诱使你把 `plan` / 缓存 / 校验 / 重算写进每个工具函数的实现里。那就又回到了 A5 与 R6.2 的那个错误，只是这次换了个地方发生。**Facade 先立住，MCP 是壳；反过来，MCP 就是第二个 `executor.ts`。**

`.sciviz` 工程文件的字段（在架构总纲 §8 的基础上，把 agent 面额外需要的补上）：

```yaml
version: 1                  # 工程格式版本（R11 的迁移判据）
graph:                      # IR：节点 + 边 + 端口描述符
datasets:                   # 数据引用
  - id: ds-1
    contentHash: sha256:... # 内容哈希是身份（R3.2），不是形状签名
    schema: { ... }
    sampleRate: 1000        # 采样率是数据属性，不是算子参数（R3.4）
    units: { ... }
environment:                # 环境锁
  nodePacks: { core: 1.4.0 }
  python: "3.12.8"
  device: { ... }           # CUDA / torch 版本（开发日志记的第三个缺口）
runs: []                    # 运行清单（G9 写入）
```

图节点上的 `group` 字段是内联复合组块定义，包含完整子图和稳定的输入、输出、参数映射。Agent 读写组块时应把它当作 IR 的递归结构；不得只保存本机可见的模块名，也不得通过重建端口顺序推测映射。`validate` / `plan` / `run` 对组块使用与画布相同的展开规则；运行清单中的内部节点 ID 带所属组实例的命名空间，可据此定位到嵌套图中的节点。

## 7. 汇报：事实由机器生成，叙述由人写

**报告不允许整体是自由散文。** 否则它与"可复现"直接冲突：一份读起来头头是道的结论，无法被第二个人（或第二次运行）验证。

```
runs/<runId>/
  run.json        # RunManifest：事实。机器生成，agent 不得手改
  report.md       # 报告：事实段（生成）+ 叙述段（可选，agent 撰写）
  patch.diff      # 本次运行相对上一个运行点的图改动
runs/index.json   # 历史索引：供 L3 漂移对比
```

`run.json` 至少含（对齐契约规格 R6.3）：

- 图指纹、算子版本集合（含 `implementationHash`）、数据集身份集合
- 参数全集、随机种子全集、环境信息
- 每个产物的身份、`simulated` 标记、缓存命中情况
- **不可复现贡献项清单**（R6：`stochastic` 与 `volatile` 必须诚实列出）
- 校验结果：L1 全部通过项与降级项、L2 抽样告警

`report.md` 的两段式：

```markdown
## 事实            ← 从 run.json 生成，逐字可核
## 叙述            ← agent 撰写，可缺省；必须只引用上段出现的数字
```

两段分开的意义：叙述段被质疑时，可以直接拿事实段去对；事实段被质疑时，可以去重跑。混在一起，两者都失去可核性。

## 8. 双向的对称性：四条可机检规则

"双向"落到实现上就是这四条。任何一条破了，项目就会慢慢退化成两套东西。

| # | 规则 | 机检方式 |
|---|---|---|
| S1 | UI 上能做的每一个图级操作，都能表达成一条补丁 op | 在 UI 动作层加断言：每个 store 动作都有一个对应的 op 名字 |
| S2 | 每条 op 的结果都落成可 diff 的文本 | 补丁写入 `patch.diff`；工程文件可 git |
| S3 | agent 的改动在界面上可见、可回滚 | 打开同一工程文件即可复现 agent 的图；回滚 = 反向补丁 |
| S4 | 契约层只有一份实现 | 静态检查：`agent-api` / `cli` 不得重新实现端口解析、校验、指纹 |

S3 是"双向"里最容易被牺牲的一条，也是最不该牺牲的一条：**agent 做的事必须留得下痕迹**。反过来说，agent 面**不需要**覆盖 UI 的全部能力——拖拽、悬浮、缩放这些交互语义只属于人，不必也不该进动作空间。对称性要求的是"结果一致"，不是"动作同构"。

## 9. 反模式

每一条都对应本项目已经踩过或正在踩的坑，不是泛泛的告诫。

| 反模式 | 为什么 | 已经发生过的证据 |
|---|---|---|
| **拿 DOM 当 agent 抓手** | 能力上限被选择器锁死；界面一改就要重写；输出是散文不是证据 | `scripts/e2e.mjs` 78 KB、`debug-module.mjs` / `tmp-repro.mjs` 用完没删 |
| **为 agent 另建一条执行路径** | 两处真相，漏改则静默 | `executor.ts` 与 `ENGINE_NODES`（A5 / R6.2） |
| **让 agent 直接写 Python 绕过图** | 边界约束、增量重算、逐边验证、有界动作空间四条同时作废 | 这正是架构总纲 §7.1 说的"agent 的替代方案是写脚本" |
| **报告是自由散文** | 结论无法被复核，与可复现冲突 | 现在只有 stdout |
| **先做 MCP / 工具面** | 编排逻辑会渗进 tool handler，形成第二套真相 | 尚未发生，但路径最短 |
| **把"跑通了"当"算对了"** | 忠实汇报一个错的数，比报错更坏 | 独立真值只覆盖 23 个算子中的 2 个 |

## 10. 验收：一次盲测，加一条常驻回归

架构总纲 §10 对 P3 的判据是"agent 不读源码即可搭出一张图并通过自检"。把它锐化成可执行的形式：

**盲测（一次性的入场判断）**

在干净的仓库里，只给 agent 三样东西：`sciviz catalog --json` 的输出、错误码表、CLI 的帮助文本。要求它完成：

1. 搭出 数据 → 分帧 → 时域特征 → 数据划分 → 评估 的图；
2. `validate` 通过；
3. `run` 并取到某个产物的具体数值；
4. **故意**破坏一次（如把拟合类输入接到非训练集），读出错误码并说明原因；
5. 修好、复验、重跑；
6. 交出 `report.md`。

判据：全程**不读源码、不看界面、不提问**。任何一步需要读源码，就是 agent 面的缺陷，而不是 agent 的能力问题。

**常驻回归（防止退化）**

把上面这套动作脚本化（`scripts/agent-blind.mjs` 或等价物），进 CI。它守住的不是某个算子，而是**整套抓手是否还自洽**——G1 的自描述性、G3 的有界性、G7 的证据完整性，任何一项退化它都会红。

这条回归与 `e2e.mjs` 的分工要明确：

| 脚本 | 守什么 |
|---|---|
| `e2e.mjs` | **交互语义**：拖拽、拉线、拒连、框选、Delete、参数内联编辑——这些只有真实浏览器能验 |
| `agent-blind.mjs` | **机器操作语义**：读、写、跑、看、报的闭环 |
| `verify-operator-truth.mjs` / `sciviz verify` | **数值正确性**：独立真值 |

三者互不替代。今天的问题是只有第一类被认真做了，而 agent 真正需要的是后两类。
